# 7z 任务：首个候选、依赖排错与复核可用性

本题要求恢复压缩包中的内容，写入 `/app/solution.txt`。十个主实验单元有八个通过官方测试；
两个失败都发生在首个候选提交之前。另一个试次正确交付了答案，却因文件指纹工具缺少 Python，
导致内部 evidence grader 出错。这三个结果分别涉及解题进度、工具可用性和官方验收。

## 复核发生了什么

- 禁网 generic_retry 生成三个候选：首个候选使用 66 次模型调用；之后两轮共增加 10 次模型调用、8 次工具调用、4,382 输出 token。最终官方通过。这里没有首版的独立官方得分。
- 禁网 transcript 使用 40 次 actor 调用与 1 次 grader 调用；grader 输出 600 token。联网 transcript 对应 29 + 1 次，grader 输出 313 token。两者一次候选即被内部接受。
- 联网 evidence 使用 35 次 actor 调用与 1 次 grader 调用。grader 发起两次 `read_artifact`，两次指纹命令都因 `python3: command not found` 以 127 退出；没有成功保存的证据记录，也没有执行验证命令。内部状态为 `grader_error`，但 actor 已写出正确答案，官方仍通过。
- 禁网 evidence 和联网 generic_retry 都耗尽约 1,800 秒，候选数为零，grader 调用数为零。因此这两条失败不能解释成“复核后改坏答案”。

## 联网 generic_retry 的具体失败路径

轨迹先出现文件工具缺少 Python、`7z2john.pl` 缺少 `Compress::Raw::Lzma` 的错误。
随后持续手工分析压缩包头、CRC、LZMA 和哈希格式，编写辅助代码，并运行字典搜索；
保存的轨迹中没有安装依赖的操作，两条搜索命令达到单次 120 秒上限。最后未写出目标文件。
这条轨迹体现的是依赖排错与交付进度的时间分配，联网许可本身没有自动带来有效工具链。

## 对后续实验的影响

本例暴露了共享运行依赖缺口。后续在缺少系统 Python 时，让文件和证据工具使用已经固定的
controller Python，保留任务原有解释器优先级。见 [修复说明](coding-actor-python-fallback.md)
和 [续跑与版本分组](coding-python-runtime-continuation.md)。本题十条原始模型试次均保留，不重采样。

案例要说明的结论是：先看是否交付首个候选，再看复核是否真正执行，最后结合官方得分和总成本
判断收益。只统计“使用了 evidence 组”会把工具失败也混入证据复核效果。
