# 证据复查定位并修复了一个边界错误

这条 case 来自固定 criterion ID 修复之前的诊断批次，任务为禁网条件下的
`regex-log / rubric_evidence`。它展示一次真实的“发现反例 → 提出修改 → 文件改变 →
反例通过”过程，同时暴露了复核门控自身的问题。

题面要求 IP 地址和日期不能紧贴字母或数字。首个候选将 IP 左边的点号也排除了：
`(?<![0-9A-Za-z.])`。证据复核工具读取实际文件并运行公开规则生成的反例：

```text
foo.1.2.3.4 2020-01-01
```

初始文件返回空列表，预期匹配 `2020-01-01`。复核器指出具体边界错误后，执行 agent
把上述片段改为 `(?<![0-9A-Za-z])`。保留的初始读回和最终提交经逐字节核验，恰好只
删除了这个点号；同一个反例随后正确返回日期。

| --- | --- | --- |

这条运行共有 43 次模型调用、47 次模型工具调用，输入 604,562 token、输出
124,601 token。虽然修复后的复核评价为 `satisfied`，旧门控仍因 criterion 名称
不匹配而拒绝结束，最终触及任务时间上限。`ce19f94` 修复了结构化评分 schema 与
门控标识之间的冲突；新版评测单独记录。

这里能证明证据复查定位并修复了一个具体行为错误，不能把它直接写成官方准确率从
0 提升到 1：首个候选只做了公开反例验证。整个旧版运行也不能作为新版效率数据。

另一个有用观察是，早期检查命令打印了 `FAIL`，但进程退出码仍为 0。日志中的
`passed` 表示命令成功退出且文件哈希未变，不能单独替代行为断言结果；本例中模型
读取了输出并正确识别错误。分析时同时审阅命令、输出和实际文件，不能只数成功退出。
