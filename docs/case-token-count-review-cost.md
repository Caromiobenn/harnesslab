# Token 计数：同分下的复核成本与检查状态

`count-dataset-tokens` 的五组 × 两种网络条件均官方通过。十份归档的 `/app/answer.txt`
都是相同的 5 字节 `79586`，SHA-256 为
`bd9cf2497a53f79be463c64572df5c98b0d3095eb621500ca45639afcf506803`。
每格独立运行一次，模型为 `deepseek-v4.1-flash-1017`，推理强度 HIGH，使用固定版本的 TB 2.1。

相同准确率下，模型调用、token 和耗时的排序不同。这个案例还显示：工具报告的成功退出码，
可能掩盖检查脚本里的错误，需要继续看实际输出。

## 复核发生在哪里

generic_retry 在首次候选后，禁网侧又使用 14 次模型响应、21 次工具调用、25,076 输出 token；
联网侧又使用 2 次模型响应、4 次工具调用、5,962 输出 token。
两侧在复查前都有工具成功读到 `79586`，最终归档也是这个值。禁网侧还重新计算并写回了相同答案。
这些记录支持“追加计算没有改变最终答案”，初始候选没有另做一次官方评分。

rubric 两组都只评估一个候选，随后给出 `satisfied`，没有再次调用 actor 修复：

| 网络 | 复核方式 | 首次候选前 actor 响应 | grader 响应 | grader 输出 token | grader 推理 token |
| --- | --- | ---: | ---: | ---: | ---: |
| 禁网 | transcript | 52 | 1 | 9,252 | 9,064 |
| 禁网 | evidence | 33 | 3 | 2,633 | 1,734 |
| 联网 | transcript | 40 | 1 | 12,227 | 12,039 |
| 联网 | evidence | 45 | 14 | 14,111 | 9,963 |

禁网 evidence 的总成本较低，但它在进入复核前就只用了 33 次 actor 响应；default 是 57 次。
本例没有复核后的修复过程，不能把这个差值解释成修复带来的收益。
另外，一次 transcript 调用就可能生成大量推理 token；仅比较调用次数会遗漏这部分成本。

## 检查数量与实际执行结果

禁网 evidence 读取了两份材料，执行一次验证；这次验证重新读取 metadata 数据，按科学领域筛选，
对不同拼接方式重新计数，再读取答案文件和哈希。联网 evidence 则读取两份材料、执行 11 次验证，
包括数据格式、字段、来源筛选、答案格式及独立重算。两侧声明的答案文件哈希在检查前后与最终归档一致。

联网第 2、10 次验证的工具输出实际上含有 Python Traceback：一次把 Arrow 文件当作 Parquet 读取，
另一次访问了空的 tokenizer 路径列表。但是命令使用 `python ... 2>&1 | grep -v PyTorch`，
最后的 grep 返回 0，两条记录因此都标记为 `passed=True`。第 7 次检查实际重算得到 `79586`，
输出 `match True`；最终官方测试也通过。因此本例暴露的是内部检查状态的含义，未造成这条试次的官方误判。

零模型诊断使用一段固定抛出异常的 Python 程序验证了管道行为：普通管道返回 0，启用 `pipefail`
后返回 1。诊断没有执行原任务代码或改写提交。后续改进验证器时，应让检查脚本明确断言条件并保留
原程序的失败退出码，再区分“命令执行成功”和“任务条件满足”。本轮继续保留实际产生的检查记录。
