# Case：工具验证通过，为什么答案仍然错了？

`chess-best-move` 的两条 mini-swe-agent 轨迹说明：验证工具只能判断传给它的
局面，无法自动保证这个局面忠实于原始图片。失败试次在错误局面上反复计算，
增加了调用和 token 消耗；成功试次正确转写局面后，更快得到了通过官方测试的答案。

两次运行使用同一任务版本、同一输入图片和文件基线，模型为
`deepseek-v4.1-flash-1017`，HIGH、streaming、每个网络条件独立运行一次。
这是 mini 基线的个案，不是四个 Deep Agents 组之间的消融结论。

| --- | ---: | ---: |
| 官方测试 | 失败，reward 0 | 通过，reward 1 |

累计 token 包含每轮重新发送的上下文，缓存 token 属于输入 token；输出长度分别
记录可见文本、推理文本和工具参数，避免只看最后一句回答。以上是原始响应的
观测量，没有通过重新运行模型补齐数据。

失败轨迹构建的 FEN 为：

```text
r1bq1r2/1p3pp1/p1n1p3/3n4/4PkbP/P1B5/1P2QPP1/R1N1K2R w - - 0 1
```

它把部分第五横线棋子放到了第四横线，并交换了白方象、马的位置。随后调用
Stockfish 和 python-chess 检查将杀；这些计算基于错误的 FEN，最终提交
`c1d3`、`g2g3`，官方测试失败。

成功轨迹使用的 FEN 为：

```text
r1bq1r2/1p3pp1/p1n1p3/3nPkbP/8/P1N5/1P2QPP1/R1B1K2R w - - 0 1
```

它提交 `e2e4`、`g2g4`，官方测试通过。两条轨迹都使用了已有的
python-chess / Stockfish 公共依赖；所提取的命令中没有 URL 命令。
N=1 的这对样本不能把差异归因于联网，也没有提供 reward hacking 的证据。

对证据复核组的启示是：先核对“图片 → 局面”的转写，再验证“局面 → 答案”。
若后续证据复核组在类似样本上更好，应查找它是否真的执行了前一步，以及这一步
花费的调用、token 和时间；不能仅凭较高准确率或更多测试次数解释机制。
