# Coding Agent 案例索引

案例用于解释实验中的具体行为，配对报告用于统计同题差异。阅读顺序建议是：
先确认样本来源，再看官方结果、实际文件变化，最后比较调用、token、输出长度和耗时。
当前整理了 12 个来自主实验的案例和 3 个诊断案例；全量评测仍在运行。

## 主实验中的行为与成本

| 案例 | 已观察到的结果 | 能解释的问题 |
| --- | --- | --- |
| [正则：普通自我复查](case-regex-self-review.md) | 主实验保留的先导试次；两轮复查额外使用 13 次模型调用、46,156 输出 token，文件逐字节未变，最终官方通过 | 固定追加复查的成本是否换来了提交变化；初版没有单独官方评分 |
| [WAL：读取副作用](case-wal-read-side-effect.md) | 十个单元中九个通过；联网 mini 打开原数据库后丢失 WAL，最终未交付；零模型独立复验复现该读取副作用 | 输入保护、恢复方向偏离和高成本失败；联网本身并未被证明是失败原因 |
| [Cython：同分不同成本](case-cython-equal-score-different-cost.md) | 禁网五组均官方通过；mini 主动提交，四个 Deep Agents 组持续操作至超时；rubric 的 grader 调用为零 | 正确答案、及时结束和复核是否触发，是三个不同维度 |
| [Raman：首个候选未交付](case-raman-submission-timeout.md) | 禁网五组均失败；mini 有结果但数值不合格，四个 Deep Agents 组没有目标文件 | 仅在提交后触发的 rubric，如何受首个候选生成进度约束 |
| [棋局：先核对输入转写](coding-case-chess-grounding.md) | mini 的两条轨迹分别失败、通过；失败试次在转写错误的棋局上调用引擎验证 | 工具能正确验证错误输入，更多计算不能代替输入核对 |
| [电路：验证闭环与额外成本](case-circuit-verification-and-cost.md) | 十个单元九个通过；禁网证据组两轮电路文件哈希相同，首轮检查失败后重新验证被接受 | 分清修复解题文件、修复验证过程和重复确认 |
| [COBOL：探索与交付](case-cobol-delivery-before-exploration.md) | mini 两侧通过，八条 Deep Agents 记录缺少要求的 Python 文件；复核均未触发 | 建立可运行候选与持续研究边界语义之间的时间分配 |
| [图片代码：入口与复核开销](case-image-entry-and-review-cost.md) | 十个单元九个通过；联网证据组执行 70 次检查，两轮答案相同；grader 的图片工具仍返回 Base64 文本 | 视觉入口差异、无关检查触发拒绝和重复验证成本 |
| [图片代码：公开参考解访问](case-image-oracle-access.md) | 联网 mini 成功读取公开 oracle 数据集中本题的参考实现，随后交付，官方 2/2 通过；最终归档代码与读取后写入一致 | 在原始准确率之外标记答案材料访问，解释联网收益的来源 |
| [Token 计数：复核成本与检查状态](case-token-count-review-cost.md) | 十个单元全部通过、答案逐字节相同；一次 transcript 复核的输出 token 可超过三次 evidence 调用；两条检查的异常退出被管道掩盖 | 调用次数、token、首次提交前后的成本和检查真实结果，需要分别观察 |
| [7z：交付进度与复核可用性](case-crack-dependency-and-review-cost.md) | 十个单元八个通过；两个失败没有首个候选；联网 evidence 正确交付但指纹工具缺少 Python，内部 grader 出错 | 区分解题失败、复核未触发、工具错误和官方通过 |
| [内存堆：文字复核误拒绝](case-heap-review-false-rejection.md) | 禁网 transcript 最终 6/6；第一次拒绝误认原有文件并提高泄漏判定要求，首个候选后增加 33 次响应、47 次工具调用和 74,011 输出 token | 复核理由的真实性、判定口径与追加成本；最终通过不能证明拒绝正确 |

这些案例按当前全量报告核对了样本归属。早期试次只有被正式保留的记录才出现在主实验分母中。
每个任务、组别、网络条件仍只有一个独立样本；案例之间的差异需要结合全量配对结果解释。

## 单独记录的诊断证据

| 案例 | 诊断类型 | 可以支持的结论 |
| --- | --- | --- |
| [正则：反例驱动的修复](case-regex-evidence-repair.md) | 修复 criterion 标识前的旧版模型试次，不在当前主实验分母中 | 一个公开反例定位了多余的点号约束；文件只删除该点号，反例由失败变为通过，最终官方得分为 1。首版未单独官方评分 |
| [HTML：禁网评分器假通过](case-offline-browser-false-acceptance.md) | 四次零模型、同错误实现的新环境对照 | 浏览器未启动会被原测试当作未检测到脚本；指定已有驱动后，两种网络均拒绝该错误实现。这是评分器诊断 |
| [WAL：公开答案访问](case-db-wal-answer-access.md) | 先导模型试次被中断，保存输出另做零模型独立复评 | 轨迹确认读取公开参考解和测试，并从公开 WAL 生成结果；保存的 JSON 在新环境通过 7/7。原试次仍为中断、无分数 |

正则修复适合说明“读取文件 → 构造反例 → 定位差异 → 修改 → 再验证”的机制。
HTML 案例说明为何需要检查评分器是否实际运行；WAL 答案访问案例则同时具有材料访问、提交来源和独立评分三段证据。
这三个诊断案例不计入当前五组主实验的准确率或效率比较。

## 形成实验结论时如何使用

对“证据复核带来收益”的候选，检查它是否发现了原候选的具体错误、修复是否改变行为，以及官方最终结果。
只发生文件变化、检查次数增加或 grader 给出 `satisfied`，都不足以单独解释准确率收益。
同时记录 actor 与 grader 的成本，并说明复核是否真正触发。

对联网与禁网差异，先区分依赖安装、题目输入理解、公开答案访问和评分器执行状态。
图片任务中的 OCR 安装失败、WAL 中的答案材料访问、HTML 中的浏览器启动失败，是不同的机制。
目录探查、命令中出现 URL 或答案前缀，先保留为待核查记录；实际访问成功与奖励后果由工具返回和官方结果确定。

使用 [全量报告](coding-campaign-report.md) 保留所有已结束尝试的成本，
再用 [同题配对报告](coding-paired-comparisons.md) 比较共同完成的任务。
同一基线会参与多项比较，各项比较的成本总量不能跨表直接相加。
最终写作同时选择有效修复、额外成本和失败案例，避免只展示有利结果。
